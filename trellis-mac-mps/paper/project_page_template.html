00 — Summary

A falsification-driven empirical study, not a success story told in advance

Apple's M5 generation introduced dedicated per-GPU-core Neural Accelerators, exposed through a new low-level API called Metal Performance Primitives (matmul2d). We asked a narrow, testable question inside a real, deployed workload — TRELLIS, an image-to-3D diffusion transformer, ported to run natively on Apple Silicon — does a hand-written kernel built on this new API actually beat PyTorch's existing native path? Mostly, no. We report that honestly, with the same rigor we'd want applied to a positive result, and then use what we learned to find a real, working, algorithmic speedup instead.

01 — Kernel-level characterization

Six operand combinations, three kernel designs, one honest ceiling

Every combination of matmul2d operand types with a half or bfloat operand clustered near 1.9× slower than native float16 nn.Linear — independent of the other operand's type. Only fully-quantized int8×int8→int32 reached parity, at a real accuracy cost.

We then built an attention kernel from scratch: a naive per-head dispatch loop, a batched-dispatch fix that falsified our own dispatch-count hypothesis, and finally an online-softmax (flash-attention-style) kernel with a real, found-and-fixed correctness bug and a verified parallelization win.

Investigated, not assumed: cooperative_tensor register-resident chaining — MPP's more sophisticated mechanism for avoiding a device-memory round trip between chained matmul2d calls — requires single-simdgroup execution scope by a hard static_assert in the actual implementation header. Our kernel's tiling needs execution_simdgroups<4>; a redesign around single-simdgroup execution would very likely mean smaller tiles and more dispatches, which we'd already shown regresses performance in a tile-size experiment. A real architectural constraint, found by reading the source, not a difficulty judgment.

02 — Algorithmic contribution

A real redundancy, a naive fix that failed, and a grounded fix that worked

TRELLIS's guidance-interval sampler calls the denoiser twice per step within its guidance window — once conditioned, once unconditioned. Caching the unconditional prediction and reusing it for several steps is a known idea in the literature. Doing it naively — freezing the raw value — produced real, visually confirmed drift that grew worse with cache interval.

We root-caused the failure against the actual mechanisms FasterCache and AB-Cache use in the published literature — neither freezes a raw branch value; both cache differences, and AB-Cache explicitly documents that a larger guidance scale amplifies stale-cache error, directly relevant given TRELLIS's configured strength of 5.0. Our fix: cache d = pred - neg_pred, and on a reuse step derive neg_pred ≈ pred_fresh - d — costing no extra model call, since the conditional prediction is already computed fresh every step.

04 — Limitations

What this isn't

Single machine (one Apple M5 Max), single model, mostly single-run wall-clock timings rather than repeated-trial statistics, and no direct benchmark against MLX or llama.cpp's Metal backend (only MLX's published kernel source as corroborating evidence). Both algorithmic results are verified on a convenience sample of objects with IoU/vertex-count proxies plus visual inspection, not a systematic perceptual study. Full discussion in the paper.
